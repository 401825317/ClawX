id: acp-compatibility-content-safety
title: ACP Compatibility Content Safety
type: ai-coding-rule
appliesTo:
  - acp-chat-experience
  - gateway-backend-communication
---

Standard ACP content is authoritative and preferred. A compatibility supplement is allowed only when it is explicitly marked by source, retained in memory, backed by approved structured runtime evidence or explicit assistant transcript evidence, and accompanied by reason-coded diagnostics. Compatibility data must never be represented as a native ACP event. It is a monotonic overlay on the owning session Turn: applying it cannot close an open ACP text segment, reorder received ACP content, or replace an unrelated message.

Approved transcript evidence has four bounded forms: asynchronous image-generation completion with proven image-generation context, including explicit internal-UI `message` tool source replies; general attachment recovery from whole-line, line-leading assistant OpenClaw `MEDIA:` directives outside fenced code blocks; successful media-Turn prefix reconciliation from the same model-authored Assistant record; and one failed live-Turn repair that can only extend the sole existing Assistant segment when both ACP prompt settlement and the transcript Assistant record prove failure. The general attachment form accepts only the documented local path, `file:`, execution-cwd-relative, HTTP, and HTTPS forms; quoted references may contain spaces, while unquoted references may not. It does not require image-generation context and projects only one ordered attachment reference per directive. A trusted image-generation source reply may provide user-facing completion or failure text. Successful media-Turn reconciliation first extracts valid attachment evidence, removes only those validated `MEDIA:` lines from a separate visible-text copy, rejects `gateway-injected` mirrors and failed Assistant records as successful final-text evidence, and may change only the last ordinary Assistant segment after the last tool when it is a strict prefix of that final text. It cannot create a message, replace divergent text, select an earlier Assistant segment, or cross a real user boundary. Failed-Turn repair cannot create a message, replace divergent text, retry, or cross the exact current user identity. Reject malformed or wrapped directives, bare or inline prose paths, unknown URI schemes, incidental tool paths, and unrelated assistant prose.

Compatibility logic must not otherwise reconstruct ordinary assistant messages, thoughts, tools, plans, permissions, file activity, or a parallel Chat history. User-side OpenClaw prompt projection may be reconstructed only from structured ACP content already present in the same timeline; generated-looking user prose is not evidence and must not be stripped or parsed. Unmatched or ambiguous evidence is skipped rather than attached by guesswork. Deduplication is turn-scoped and uses only a Main-authorized opaque identity; native ACP resource content wins over equivalent compatibility evidence, generated-image evidence remains inline, and attachment access is monotonic: `pending -> unavailable -> available` is allowed, while an available attachment cannot regress to pending or unavailable. A full native Assistant replacement preserves already resolved compatibility media. Navigation or a later prompt does not invalidate accepted delivery for another Turn; only cancellation of that Turn, a superseded generation, an expired bounded operation, or evidence mismatch may reject it.
