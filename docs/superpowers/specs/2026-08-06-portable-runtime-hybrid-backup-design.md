# Windows 便携运行时混合备份设计

## 目标

UClaw 在 Windows 便携模式下继续使用本机 `%LOCALAPPDATA%` 目录运行 OpenClaw，避免普通 U 盘承受实时随机读写；同时只把发生变化的持久数据增量写入 U 盘，保证用户更换电脑后仍能恢复配置、账号、Agent、会话、工作区及其他已有 OpenClaw 状态。

成功标准：

- 正常运行期间不再每轮向 U 盘完整复制数千或上万个文件。
- 没有文件变化时不写 U 盘；有变化时只写变化文件和一份小型清单。
- 同步中断、U 盘拔出或文件正在写入时，上一份完整备份仍然可恢复。
- 新版本可恢复 v2 增量快照，也继续兼容现有 v1 完整快照。
- 不改变 Gateway、聊天信息流和 OpenClaw 的运行目录语义。

## 已知问题

当前 `syncPortableRuntimeSnapshot()` 每次创建一个新的完整目录，并递归复制全部非排除文件。用户日志显示：

- 约 13,800 个文件的一轮快照需要 10 至 15 分钟。
- 约 5,950 个文件的一轮快照需要 5 至 8 分钟。
- Chromium 的 Cookies、Session 等文件在复制期间持续变化，会导致整轮快照失败并删除。
- `inFlight` 只能阻止重叠执行，不能减少扫描、复制和失败后清理产生的 I/O。

因此，仅延长同步间隔不能解决根因。

## 总体架构

### 本机运行层

OpenClaw 继续使用当前本机运行目录：

```text
%LOCALAPPDATA%\UClawRuntime\profiles\<portableId>\openclaw-state
```

所有高频读写继续发生在本机磁盘，UClaw 不拦截 OpenClaw 的文件写入。

### U 盘持久层

U 盘新增 v2 备份目录：

```text
UClawData\runtime-snapshots-v2\
  objects\<sha256-prefix>\<sha256>
  manifests\snapshot-<timestamp>-<uuid>.json
```

- `objects` 保存按内容哈希寻址的文件。相同内容只保存一次。
- manifest 描述某个完整恢复点中每个相对路径对应的对象哈希、大小和修改时间。
- manifest 使用临时文件写入，完成后原子重命名。只有完成重命名的 manifest 才是可恢复快照。
- 保留最近 3 个完整 manifest；清理不再被这 3 个 manifest 引用的对象。

该结构不依赖 NTFS hardlink，兼容 Windows 常见的 NTFS、exFAT 和 FAT32 U 盘。

## 增量同步流程

1. 每 5 分钟在本机运行目录执行一次元数据扫描。
2. 以相对路径、文件大小和 `mtimeMs` 与上一份 manifest 比较。
3. 未变化文件直接复用上一份 manifest 中的对象，不读取文件内容，也不写 U 盘。
4. 新增或变化文件经过稳定性检查后计算 SHA-256，只在对象不存在时写入 U 盘。
5. 已删除路径从新 manifest 中移除。
6. 所有可纳入本轮的变化处理完成后，原子发布新 manifest。
7. 如果扫描结果与上一份 manifest 完全相同，不创建新 manifest，不执行 U 盘写入。

扫描只读取本机目录元数据。实现使用有限并发，避免同时发起上万个文件系统请求或占用过多内存。

不使用 `fs.watch` 作为正确性来源。Windows 文件监听可能丢事件；后续如果需要，可仅把它作为提前触发扫描的性能提示。

## 持久数据边界

默认延续当前 `shouldSkipRuntimeEntry()` 的排除规则，继续排除根目录下的日志、缓存、临时目录、编译缓存，以及 `.lock`、`.tmp` 文件。快照服务自身维护的 `.uclaw-runtime-state.json` 也属于本机运行元数据，必须排除，避免一次成功同步制造下一轮文件变化。

另外排除 Chromium 中可自动重建且高频变化的缓存目录，例如 Cache、Code Cache、GPUCache、Crashpad 和临时下载数据。Cookies、Local Storage、IndexedDB 等登录态数据仍属于持久数据，不能整体排除。

持久数据边界使用明确路径规则维护，不根据文件数量或大小自动猜测，避免误删用户数据。

## 活跃文件与一致性

- 变化文件复制前后比较大小和修改时间；不稳定文件最多重试 3 次。
- 已存在上一版本对象时，本轮继续引用上一稳定版本，不让单个活跃文件导致整个快照失败。
- 首次建立 v2 基线时，如果必要文件没有上一稳定版本且持续变化，本轮不发布 manifest，下一轮或退出同步时重试。
- SQLite 数据库及其 WAL/SHM 文件按文件组处理：组内任一文件不稳定时，整组沿用上一稳定版本，避免混合新旧数据库文件。
- 应用正常退出时，先停止 Gateway 及其管理的浏览器进程，再执行一次有时间上限的最终同步，提高最后一次快照的新鲜度。

同步失败只记录日志，不阻塞 Gateway、主窗口或应用正常使用。

## 恢复与升级兼容

恢复顺序：

1. 查找最新的完整 v2 manifest，校验路径安全和对象是否存在后恢复。
2. 没有可用 v2 快照时，继续使用当前最新完整 v1 快照。
3. 两者都不存在时，继续使用现有 legacy state 恢复逻辑。

首次升级不删除 v1 快照。只有 v2 成功发布并经过一次恢复验证后，旧 v1 快照才进入后续清理范围；首版实现保守保留 v1，不主动迁移或删除。

恢复过程中禁止 manifest 中的绝对路径、`..` 路径穿越和符号链接。对象缺失或哈希不匹配时放弃该 v2 快照并回退到上一完整恢复点。

## 生命周期

- 启动：只启动轻量定时扫描，不立即执行完整复制。
- 周期同步：每 5 分钟检查一次；无变化直接结束。
- 同步中再次触发：复用当前 `inFlight` 互斥，不并发执行。
- 正常退出：停止周期任务，停止 Gateway 及其管理的浏览器进程后执行最终同步。
- 异常退出或拔盘：未完成对象和临时 manifest 不参与恢复；下次同步清理孤立临时文件。

## 日志与可观测性

每轮只记录汇总信息：

- 扫描文件数、变化文件数、复用文件数。
- 写入对象数和字节数。
- 不稳定文件数和沿用上一版本的文件组数。
- 扫描耗时、U 盘写入耗时、总耗时。
- 无变化跳过、U 盘不可用、快照发布成功或延期。

日志不输出文件内容、凭证或完整敏感路径。

## 测试范围

### 单元测试

- 首次建立 v2 基线并恢复。
- 无变化时零对象写入且不创建新 manifest。
- 单个文件变化时只写一个新对象。
- 新增、修改、删除文件后的恢复结果正确。
- 不稳定文件沿用上一稳定版本。
- SQLite 文件组不会混合新旧版本。
- 同步中断后仍恢复上一完整 manifest。
- 对象缺失、哈希错误和路径穿越时拒绝快照并回退。
- 保留最近 3 个 manifest 并安全回收无引用对象。
- v2 不可用时回退 v1。

### Windows 便携包验证

- NTFS、exFAT U 盘各验证一次。
- 5,000 和 15,000 文件样本下记录首次基线及增量耗时。
- 聊天、浏览器登录态和工作区变化后换电脑恢复。
- 同步中拔盘、只读 U 盘、空间不足和应用强制结束。
- 从已有 v1 快照升级，不丢失旧恢复能力。

## 风险与控制

- `mtimeMs + size` 理论上可能漏掉同大小且时间戳不变的外部改写。退出最终同步和定期校验可降低风险；首版不对所有未变化文件重复计算哈希，否则会重新引入全量读取。
- FAT32 不支持超过 4 GiB 的单文件。写对象前检测并记录明确错误，不让整个应用失败。
- 对象存储会增加实现复杂度。限定为单一 v2 格式，不增加用户可配置策略和多套同步模式。
- 首次 v2 基线仍需完整写入一次，无法消除；优化目标是消除之后每 5 分钟的重复全量写入。

## 非目标

- 不把 OpenClaw 实时运行目录迁回 U 盘。
- 不修改 OpenClaw、Gateway 或聊天信息流协议。
- 不实现云同步、跨设备并发合并和多版本用户界面。
- 不承诺异常拔盘前最后几秒的数据一定已经同步，但必须保证上一完整恢复点可用。
